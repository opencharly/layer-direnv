# 2026.267.2235 — fix: drop the invalid sh direnv hook and assert the shell guards

## Summary

Drop the invalid `sh` direnv hook and assert the shell guards.

The direnv candy's generic `shell: init` is substituted per shell, so it emitted
`/etc/profile.d/charly-direnv-sh.sh` with `eval "$(direnv hook sh)"`. Upstream
`direnv hook` supports **bash/zsh/fish/tcsh but not `sh`**, so that body errors
(`direnv: error unknown target shell 'sh'`) on every shell that sources it — and
`/etc/profile` sources **every** `profile.d/*.sh` in every POSIX login shell, so
the error spammed every login, alongside the cross-shell zsh syntax error.

### The fix

- Opt `sh` out with an empty `sh: {}` override (an empty per-shell block makes the
  compiler **skip** that shell), leaving bash + zsh — guarded to their own shell by
  the companion sdk mechanism fix — plus the fish `conf.d` hook.
- Plan checks now assert the bash + zsh drop-ins carry their guards, **no** `sh`
  drop-in is baked, and **the observable cross-shell regression**: sourcing the
  zsh drop-in under bash must produce zero errors (the zsh body uses zsh-only
  syntax, so an unguarded drop-in errors under bash). The bash-drop-in-under-sh
  direction is NOT asserted because it is not behaviorally observable on these
  images — `/bin/sh` is bash and the bash body is POSIX-common (verified live).
- Description + embedded skill prose updated to the bash/zsh reality (claim-keyed
  sweep; exact command + output below).

Companion PR: **`opencharly/sdk` #282** (merged, tag `v0.2026267.2215`) — the
mechanism half (`GuardShellDropin`) that runtime-guards each POSIX drop-in to its
own shell. The `sh: {}` opt-out's empty-skip behavior lives in
`sdk/deploykit.ResolveShellSpec` (pre-existing).
